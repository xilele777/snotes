# 启动性能排查与复测

## 已确认的瓶颈

- v0.23.4 起将 Vditor vendor 整目录纳入 PWA 预缓存：417 个文件、22,071,450 字节，包含未使用的图表、公式、语言、字体与主题。Chrome 对 CacheStorage 的磁盘估算还包含 padding，不能将站点占用当成笔记正文大小。
- 元数据每一页读取整张笔记表，克隆所有正文；正文逐条提交事务，50 条一批串行下载。空的笔记本同步也会触发列表重读。
- 编辑器依次加载语言包、Lute，图标使用同步 XHR；初次正文重复解析，按键触发整篇 Markdown 序列化，DOM 观察器频繁扫描全文。
- 长列表为每条笔记创建 Vue 组件；每次自动保存重新读取完整列表。

现在核心资源并行异步加载，长列表仅渲染视口附近的行，正文最多三批并发且每批完成即落库显示。检查待上传任务和正文写入保持在同一事务内；任意批次失败都不推进同步游标，并等待所有在途批次结束再允许重试。

## 可复现方法

先运行 `npm run build`，再运行：

```bash
node scripts/profile-startup.mjs --runs 3
node scripts/profile-startup.mjs --baseline <旧版本构建的dist目录> --runs 3
```

结果写入 `tmp/startup-profile.json`，可用 `--output` 指定文件，`--current` 指定当前构建目录。比较基线为 v0.24.0（9c59602，包含 v0.23.4 引入的编辑器缓存行为）。比较时关闭其他测试和构建任务，使用三轮中位数，避免宿主机争用 CPU 干扰结果。

脚本启动临时本地 HTTP 服务，使用 500 条合成中文笔记和模拟 API，不访问生产数据。Chromium 采用 390×844 视口、4 倍 CPU 降速、4 Mbps 下行、40 ms 网络延迟。衡量：

- 清空站点数据后，完整笔记数量显示的时间。
- 列表显示后点击首条笔记，到编辑器正文可见的时间。
- 已有本地数据后刷新，到上次编辑正文可见的时间。
- `navigator.storage.estimate()` 的站点总占用及分类、CacheStorage 条目、同步 XHR 与主线程长任务。

提供基线时，额外在同一 origin 从旧版切换到新版，验证 Service Worker 激活后旧图表等预缓存被删除，500 条 IndexedDB 笔记仍保留。存储估算可能滞后于缓存删除，升级检查以缓存键和数据库行数为准。

这些结果用于相同环境的前后比较，不代表真实手机、真实服务端或任意网络的绝对耗时。首次清空后仍需要传输用户正文，无法对任意笔记量和带宽承诺一秒恢复完全部内容。

## 离线与 Lighthouse

核心编辑和已同步正文保持离线可用。公式、流程图等额外渲染器首次使用时需要网络，成功使用后由运行时缓存支持后续离线访问；不再为未使用功能提前下载整套资源。

Lighthouse 关于浏览器扩展和 IndexedDB 的提示是审计环境提醒，不足以判定 IndexedDB 本身导致慢。使用无扩展的独立配置分别测空缓存和已有数据的刷新；若只在无痕空缓存测一次，会遗漏日常本地启动体验。不要通过删除用户正文和未同步修改来提高评分。

自动化回归覆盖元数据先显示、正文未下载时禁止编辑、本地输入防覆盖、失败批次不推进游标，以及桌面/手机长列表末尾、返回恢复、搜索与键盘导航。
