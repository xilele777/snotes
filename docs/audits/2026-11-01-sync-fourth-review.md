# 同步机制第四轮复核（2026-11-01，未发布）

基线为应用 1.0.5 加前三轮工作区修复。本轮重点复核冲突副本与上传确认之间的事务边界，以及旧远端清单对本地待删除任务的影响。没有修改生产数据，没有发布。

## 冲突副本在整轮失败时丢失

旧实现先在 `pushOnce()` 中确认并移除上传任务，将 `previous_content` 仅保留在返回结果；引擎等整个上传队列结束后才创建冲突副本。若另一条并发上传返回 `sync_reset_required`，整轮直接抛错，已成功请求的副本不会被保存。此时原上传任务已经出队。

新增测试复现：两条正文并发上传，一条成功并带回冲突正文，另一条要求恢复对账；原实现没有副本。修复后，副本创建、入队、原任务 ACK 在同一个 IndexedDB 事务内完成，独立于其他上传的最终结果。副本落库后发送界面刷新通知，引擎不再重复创建。

另外验证了副本写入失败时 ACK 回滚，原任务仍在，以及请求期间用户彻底删除原笔记时，已返回的冲突正文仍可另存。

## 响应丢失时短正文冲突没有服务端兜底

普通历史快照有时间与改动量节流。连续修改短正文时，被冲突覆盖的版本可能没有历史；服务端成功写入而响应丢失后，客户端重试会走正文相同的幂等分支，不再带回之前的冲突正文。

现在非空冲突正文无论改动量大小，都在正文条件更新的同一个数据库事务中保存历史。历史 INSERT 紧随条件正文 UPDATE，并受 `changes() = 1` 约束：条件更新失败时不为未覆盖的版本留快照。发生真实冲突时省去原先事务外的历史检查路径。普通无冲突编辑继续使用原有节流规则。

冲突历史按捕获时刻计时，避免长期未编辑的正文因旧更新时间超过保留期而在刚保存后立刻被修剪。仍遵守最多 20 条、30 天的历史保留限制，不是永久审计日志。

验证包含：

- 提交成功后立即抛错，模拟响应丢失；被覆盖正文仍在历史中，重试不重复生成同一快照。
- 事务最后注入 SQL 错误；正文与冲突快照一起回滚。
- 条件更新前插入另一次编辑；失败的尝试不保存错误快照，重试只保存真正被覆盖的版本。
- 连续短冲突遵守数量限制，旧笔记冲突不会立即过期。

## 待上传的彻底删除被旧清单重新下载

本地彻底删除会移除笔记并保留 purge 任务。任务退避、永久失败或恢复对账时，pull 仍可能看到服务器上的旧记录；旧实现把它当新笔记重新插入并下载正文，造成删除后又出现的现象及无用流量。

现在规划下载时排除存在 purge 任务的笔记，并在插入元数据的同一事务里再次检查，覆盖规划期间用户删除的情况。正文落库原有的存在性检查保留。purge 任务继续等待上传，游标仅按原有成功条件推进。

## 验证与限制

- `npm run test:all`：前端/共享 828 项、Worker 207 项、自托管服务端 74 项，共 **1109 项通过**。
- `npm run build`：类型检查、Vite 构建与 PWA 生成通过。
- `git diff --check` 通过。
- 这次解决的是异常路径数据保护及待删除笔记的重复下载，没有生产鉴权接口的耗时测量，不能据此判断 Cloudflare 是主要延迟来源。
- 响应完全丢失时，客户端无法凭空恢复 `previous_content` 并自动创建可见副本；新版服务端保存的历史是恢复入口，仍受历史保留规则限制。
- 没有自动修复旧版已经丢失的副本或历史；客户端与服务端修复都需要发布才能完整生效。
