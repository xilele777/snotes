# 同步机制排查（2026-11-01，未发布）

审计基线：根目录应用版本 1.0.5。用户反馈主要是每次打开或刷新时同步持续较久。本轮修复与验证记录已分项提交，未打标签、推送或部署，线上仍需独立复测。

## 与打开、刷新直接相关的发现

正常启动先读取 IndexedDB，再在后台同步。`main.ts` 中启动引擎和随后调用 `syncNow()` 会复用同一个在途 Promise，没有发现由这几次调用导致重复整轮同步。本地已下载的笔记正文不依赖云端返回才显示。

已经有同步进度、没有待上传改动、也不需要全量核对的典型启动，原内容同步路径有五次串行请求：

1. `/api/sync/instance`：实例身份。
2. `/api/sync/checkpoint`：笔记进度有效性。
3. `/api/knowledge-bases/sync/checkpoint`：笔记本进度有效性。
4. `/api/sync/pull`：笔记、分组增量。
5. `/api/knowledge-bases/sync/pull`：笔记本增量。

打开次数另外发请求，与上述内容同步并行。首次建立本地数据库、正文更新、恢复对账、笔记本每天一次的完整核对会增加请求，不能用上述五次概括所有情况。

已将前两项独立检查并行，仍等待两个请求全部完成后才离开检查阶段；恢复后上传前的核对和实例围栏未移除。典型路径从五层网络等待降为四层，请求数不变。此前笔记本目录逐个下载；现在每批最多三个请求同时执行，各批全部收尾后再继续，失败时不推进同步游标。收益取决于网络延迟与笔记本数量，不代表真实线上耗时已经测得改善。

## 已修复的确定性问题

### 笔记本增量分页提前结束

服务端在增量模式下返回 `next_id: null`，以 `next_after` 表示是否还有下一页。客户端却把 `next_id === null` 当成所有模式的结束条件。一页最多 50 个笔记本变更，超过时后续页被跳过，但本地游标仍推进至 `until`，普通增量轮次不再补回遗漏。

现在分别判断完整清单与增量分页的终止条件。新增 51 个变更的回归用例，并验证第二页失败时游标仍停留在原位置。旧版本已经跳过的内容仍需完整清单核对才能补回，现有每天一次的核对机制保留。

### 网络失败后仍耗尽整条上传队列

笔记上传虽然最多三个并发，但连接中断后仍会继续启动后续笔记的请求；笔记本上传也逐个继续尝试。单请求超时为 15 秒。例如预检查成功后网络中断，30 个独立笔记请求若都等满超时，单是上传阶段就可能累计约 150 秒，随后还会继续尝试拉取。

现在遇到连接错误、408、429 或 5xx，会停止安排剩余上传，等待已发出的请求收尾。已成功的确认和冲突副本仍保存，未发送任务原样保留；当前轮跳过后续下载，下一轮或手动重试继续。永久业务错误仍按原规则处理。

### 请求期间再次打开同一笔记，统计可能漏同步

旧实现仅按笔记 ID 清理已上报队列。如果请求期间同一 ID 的打开次数增加，旧响应也会把它清出队列，新计数直到下次打开才有机会补传。

现在确认 ID、计数及最后打开时间均与请求快照一致后才清理。这个问题涉及打开统计，不是正文启动速度的主要原因。

## 线上只读测量及其限制

当前机器对生产站点 `/api/health` 连续五次读取均为 200，耗时为 1124、727、189、200、204 毫秒；响应带有 `server: cloudflare`。这是网络请求总耗时，包含连接建立等因素，不能视为 SQL 查询耗时。

该健康接口不访问 D1。另尝试使用已有本地开发配置访问实例身份接口，返回 401 后即停止，没有得到生产鉴权接口的有效耗时数据。因此本轮不能判断 D1 的运行地域、查询耗时或排队是否是主因，也不能把这组测量当作用户设备的网络表现。

代码层面的串行请求会叠加网络等待，可以解释部分启动体感；是否还存在生产数据库瓶颈，需要在实际登录会话中记录请求瀑布、各接口耗时以及是否触发全量核对后才能确认。没有据此修改 Cloudflare 部署地域、数据库或生产配置。
