# 同步机制第三轮复核（2026-11-01，未发布）

基线为应用 1.0.5 加前两轮修复，第二轮工作区改动保留。本轮重点是上传确认、请求乱序、删除与队列交错，而不是继续扩大请求并发。下述问题均有回归测试覆盖；版本误标、离线清空、旧队列快照、统计超限、旧计数覆盖和本地落库失败提前结束均先运行测试复现，再修复。

## 1. 上传响应中的版本号被错误当作本地内容已同步

旧 `finalizeAck()` 无论上传正文还是单个属性，都把响应的 `version` 和 `prop_version` 写回本地。响应包含的是服务端计数，并不包含另一台设备更改后的完整属性或正文。

- 另一台设备设置了星标，本机上传正文、置顶、删除或恢复后误推进 `prop_version`，下一次 pull 因版本相同跳过属性更新，星标长期不一致。
- 本机先上传属性、再上传离线正文时，属性 ACK 可以把尚未下载的远端正文版本写成下一次 PATCH 的基线。服务端误以为本机已见过那份正文，不返回冲突副本。

现在只有正文上传和确实接受了请求内容的创建才确认正文版本；部分属性及状态操作不确认完整属性投影，交给后续 pull 应用。已有本地编辑的 seq 和 outbox 保护保留。

## 2. 创建重试及创建后的并发修改误确认

创建已成功但响应丢失，另一台设备随后编辑，旧创建请求重试会返回服务端当前版本。此前客户端直接将其写成 `body_version`，实际上本地还是最初正文，后续下载被跳过。

创建接口增加向后兼容的 `replayed` 字段：幂等重放不代表接受了本次内容，客户端据此等待下载。实际新插入只确认自身写入的初始版本，避免插入后读取 ACK 时把别端刚提交的版本一起确认。复活墓碑仍确认本次写入的实际版本。

创建重试修复需要新版客户端和服务端配合。旧服务端不提供 `replayed` 时仍走兼容行为，不能认为该边界已得到同等保护。

## 3. 取消后的旧任务继续上传，离线清空可能让笔记重新出现

旧上传队列按本轮开始时的快照发送。前面的请求未完成时，用户彻底删除或再次编辑笔记，旧快照仍可能发出。

现在发送前重新读对应任务，检查它仍存在且 seq 未变。被删除或替换的任务跳过，新编辑留在队列供后续同步；已经发出的请求仍等待确认。

旧 `purgeTrash()` 只删本地笔记并排入一条全局清空请求，未清除这些笔记的 create/body/trash 任务。全局清空与单条上传属于不同并发链，可能先清空，再由旧创建、删除请求把笔记放回云端回收站。

现在在同一事务内删除这些笔记的旧任务，并为本次确认的每个 ID 排入单条 purge。删除对象固定，不会顺带清理确认后新出现的云端回收站内容。

代价：大量笔记清空由一个全局请求改为逐条请求，仍最多三个并发，会增加这一场景的网络请求数量。旧版已经排入的全局清空任务保留兼容处理，无法仅凭旧 payload 推断当时确认的全部 ID。

## 4. 打开统计超限和乱序

- 服务端每次最多接受 500 条统计，客户端此前发送整个 dirty 队列。超过 500 条会每次都返回 400，重试也无法前进。现在每轮最多发送 500 条，仅确认发送且计数未改变的条目，其余保留到下一轮。
- 多标签页共用设备 ID，旧请求晚到会把新计数覆盖。例如先到 5 次、后到旧的 2 次，服务端最终变成 2。现在 count、last_open_time 和 update_time 使用单调合并，旧请求不会降低累计值。

## 5. 本地数据库错误使上传轮次过早结束

上传 ACK 落库失败后，如果记录重试状态也失败，异常会跳出请求处理。原 `Promise.all` 立即拒绝，但其他请求可能还在执行，下一轮可以与它们重叠。

现在任何未处理的上传工作线程错误都会停止继续调度；使用 `Promise.allSettled` 等待其他在途上传及落库完成后才结束本轮。测试注入本地读取错误，验证另两条成功请求仍完成确认、第四条不发送、当前轮不会提前退出。
