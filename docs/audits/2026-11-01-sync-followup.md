# 同步机制第二轮排查（2026-11-01，未发布）

基线：应用版本 1.0.5，Git `454c647`，已包含上一轮同步修复。本轮修改保留在工作区，未提交、打标签、推送或部署；发布记录追加在 `CHANGELOG.md` 的 Unreleased 下。

## 已修复

### 联网后笔记本仍处于上传退避

`retrySyncNow(false)` 在 online 事件中只解除普通笔记 outbox 的退避，未调用 `retryKnowledgeBases()`。笔记本失败重试最长退避 256 秒，联网后即使引擎开始同步，任务也可能继续被跳过，随后还需等下一轮轮询。

现在两种队列都会在网络恢复时解除临时退避。笔记本的 `blocked` 冲突任务仍保持阻塞；已经发送的操作 ID、请求快照及错误信息保留，避免把请求结果未知的写入变成另一笔操作。

### 三个并发请求按整组等待，慢请求拖住后续下载

正文每批 50 条、笔记本目录每次一个请求。原实现每组三个请求全部完成后才开始下一组，前一组只剩一个慢请求时，另外两个槽位会闲置。

现在使用共同的有界调度函数，单个请求及其本地落库完成就补上下一个任务，最多三个并发。遇到失败停止启动后续任务，等待所有在途请求及落库完成后才返回错误；同步游标仍只在所有必要下载成功后推进。

新增回归覆盖：201 条笔记中的慢正文批次不阻塞后续批次、笔记本目录的同类情形，以及失败后剩余批次不再启动、在途成功内容仍落库。原有下载期间本地编辑保护测试继续通过。

固定延迟模拟：9 个任务延迟为 `[80, 5, 5, 80, 5, 5, 80, 5, 5]` 毫秒，并发上限均为 3。当前机器三轮实测如下（实际定时器受到系统调度影响）：

| 轮次 | 原整组等待 | 新持续调度 |
| --- | ---: | ---: |
| 1 | 282 ms | 141 ms |
| 2 | 280 ms | 140 ms |
| 3 | 282 ms | 141 ms |

这只是调度模型的模拟对照，不含 HTTP、D1 或 IndexedDB；不能当作生产同步提速比例。只有一到三个下载任务、或者没有正文/目录变化时，这项优化收益有限。

### 同步进度校验重复读取数据库

原 `validCheckpoint()` 先单独读取实例 epoch，再执行真正的 checkpoint 查询；笔记 checkpoint 路由还会先读取一次时钟，重复检查后续 SQL 已检查的条件。

现在实例 epoch 与 checkpoint 的时钟、revision、有效期和 domain 在同一条 SQL 中检查；路由去掉冗余的时钟读取。一次 `validCheckpoint()` 从两次数据库调用减为一次，同时避免两次查询观察到不同数据库状态。

两个同步域都有非零游标的普通增量轮次中，笔记 checkpoint 少两次数据库调用，笔记本 checkpoint、笔记 pull、笔记本 pull 各少一次，合计减少五次。客户端 HTTP 请求数量与前置恢复检查顺序不变。新增共享契约测试在 Worker 和自托管 SQLite 中都验证单次数据库调用、部署 epoch 区分和缺失时钟时拒绝校验；现有备份恢复、过期和跨域校验继续通过。

## Cloudflare 与剩余限制

本轮确认了客户端额外等待和服务端重复数据库访问，没有取得用户实际登录会话的生产请求瀑布或生产 D1 分段耗时。因此不能判定 Cloudflare 网络或数据库是主因，也没有修改部署地域、数据库配置或生产数据。

每日笔记本完整核对仍会下载目录；恢复对账仍会下载需要核对的内容。这些路径包含引用状态刷新和数据恢复语义，不能仅凭版本相同就跳过。普通笔记的属性更新仍逐条事务落库，本轮没有测得其在用户实际数据规模下的占比，未扩大修改范围。
